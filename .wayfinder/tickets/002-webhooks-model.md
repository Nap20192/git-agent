# Модель вебхуков GitHub/GitLab

Type: wayfinder:grilling
Status: closed
Assignee: vnkjd
Blocked by: —

## Question

Какие события рождают Событие, кто регистрирует webhook, секреты подписи, различия GitHub vs GitLab, дедупликация, события без активной связки, dev без публичного URL.

## Answer

- **Все действия провайдера** → События: хук вешается на всё, всё журналируется и публикуется. Реагирует ли Сборка — не забота вебхук-слоя.
- **Идемпотентность**: дедуп-ключ Экземпляра = (Сборка, repo, `dedup_key`); `dedup_key` = commit_sha для коммитных событий (push/PR), иначе `event_id` — бескоммитные проходят поштучно.
- **Регистрация хуков — сам backend**: пользователь «подключает» Репозиторий (выбор из списка по OAuth-токену), backend через API провайдера создаёт hook (URL из `WEBHOOK_BASE_URL` + секрет). Появляется явный акт «подключённый Репозиторий».
- **Секреты**: случайный per-repo секрет в БД; GitHub — HMAC `X-Hub-Signature-256`, GitLab — сравнение `X-Gitlab-Token`. Шифрование хранения — решается вместе с OAuth-токенами (тикет 003).
- **Невалидная подпись / неизвестный репо**: всегда `200` + дроп + внутренний лог (не светим наружу ничего).
- **Дедуп доставок**: журнал событий, unique (provider, delivery_id); повтор = no-op.
- **Transactional outbox**: обработчик вебхука в одной транзакции пишет журнал + outbox-строку; отдельный паблишер разгребает outbox → Rabbit. Он же — механизм ре-публикации после смерти раннера.
- **Dev**: туннель cloudflared, публичный URL в `WEBHOOK_BASE_URL`.
