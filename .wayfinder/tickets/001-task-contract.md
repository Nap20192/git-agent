## Question

Что такое Таск как сообщение и ресурс: схема сообщения в RabbitMQ, жизненный цикл и статусы, идемпотентность, кто репортит завершение, поведение при падении агента посреди Таска.

## Answer

Таск как сущность **отменён** (и backend-Ран тоже). Вместо него:

- **Событие** — тонкий факт с вебхука, летит в RabbitMQ: `{event_id, provider (github|gitlab), repo, action (push|pr|tag…), commit_sha/ref, user_id}`. Без секретов и LLM-конфига.
- **Сборка Агента** — определение в БД: LLM connection, sandbox connection, промпт/пресет памяти. Привязка `repo → Сборка` один-к-одному в v1 (профили = несколько Сборок — потом).
- **Экземпляр Агента** — живая реакция на Событие: поднятый из Сборки агент, чекпоинт-тред, статус, результат. Уникален по (Сборка, repo, commit) — идемпотентность здесь, второй не поднимаем.
- Слоты держит **Python-раннер** (нынешний агентский процесс станет консьюмером Rabbit — отдельное усилие, здесь только контракт). Go-сервис События публикует и ведёт БД, агентов не исполняет.
- Никакой ack-семантики как гарантии: auto-ack, гарантии дают БД + чекпоинты. Раннер умер (heartbeat протух) → backend видит working-Экземпляры мёртвого раннера → ре-публикует Событие → другой раннер Возобновляет с чекпоинта.
- Результат Экземпляр пишет в БД сам, через тулзу агента. Одна общая Postgres (подтвердить границы схем — в тикете «Схема БД»).

**Пересмотрено тикетом 004**: Экземпляр стал долгоживущим агентом Репозитория — один на (Сборка, repo), статусы down/running; идемпотентность — журнал обработанных Событий внутри Экземпляра, а не уникальность Экземпляра по коммиту.
