# Сборки Агентов и реестр раннеров

Type: wayfinder:grilling
Status: closed
Assignee: vnkjd
Blocked by: —

## Question

Состав и владение Сборками Агентов; раннеры: регистрация, heartbeat, слоты, API; как backend понимает, что Экземпляры мёртвого раннера пора ре-публиковать. Плюс запрос пользователя: прямое взаимодействие с агентом через его API, экземпляры «подняты или нет».

## Answer

- **Экземпляр Агента пересмотрен** (уточняет тикет 001): это **долгоживущий агент Репозитория** — один на (Сборка, Репозиторий), один чекпоинт-тред, копящий знание о репо. События будят его и доливаются в тред; чат пользователя идёт в тот же тред. Идемпотентность — журнал обработанных Событий внутри Экземпляра (dedup_key из 002), а не уникальность Экземпляра по коммиту.
- **Статусы Экземпляра**: `down` (чекпоинт в БД, в памяти нет) ↔ `running` (в слоте раннера). Инвариант single-running (БД). Смерть раннера (heartbeat-таймаут) ⇒ его Экземпляры `down`; подъём заново — с чекпоинта.
- **Поднимают двое**: Событие (раннер берёт из очереди и поднимает сам) и пользователь (backend просит раннер поднять для чата).
- **Песочница Экземпляра — решение изменено (2026-09) на авто-создание при запуске**: нет живой (не привязана / dead) в момент /trigger, raise или chat — hub сам создаёт её из sandbox_connection Сборки (тот же путь, что POST /api/sandbox-instances) и привязывает, и только потом публикует Событие / зовёт раннер; ручные create/link/kill в UI остаются, раннер по-прежнему connect-only.
- **Опускание**: idle-таймаут — нет Событий и чата N минут ⇒ выгрузка, слот свободен.
- **Путь запроса пользователя**: только через backend (`/api/instances/{id}/chat` и т.п.) — backend находит/поднимает Экземпляр через API раннера и проксирует. Фронт топологию раннеров не знает.
- **Сборка** = LLM connection + sandbox connection + промпт + пресет памяти + лимиты; создаёт пользователь через API backend; есть дефолтная.
- **Раннер**: саморегистрация при старте (имя, адрес API, число слотов), heartbeat; смерть — пара пропущенных heartbeat'ов.
