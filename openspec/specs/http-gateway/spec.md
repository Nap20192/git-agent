## Requirements

### Requirement: HTTP-доступ к Ранам по контракту OpenAPI

Система SHALL предоставлять HTTP API по машинному контракту `frontend/docs/openapi.yaml` (авторитетный wire-спек: пути, схемы, camelCase-поля). Submit через HTTP MUST сохранять контракт `durable-runs`: идемпотентность по идентичности, ответ несёт disposition (created / resumed / attached / already_succeeded).

#### Scenario: Submit того же Рана дважды

- **WHEN** клиент дважды отправляет POST /runs с одной идентичностью
- **THEN** второй ответ ссылается на тот же Ран с честным disposition, второй Ран не создаётся

#### Scenario: Отмена и Возобновление

- **WHEN** клиент вызывает cancel или resume для существующего Рана
- **THEN** действия транслируются в отмену/Возобновление durable-рантайма, ответ отражает новое состояние Рана

### Requirement: SSE-стрим событий с реплеем

События Рана SHALL отдаваться как Server-Sent Events с реплеем по курсору: подписка с курсором возвращает события строго после него; курсор старше буфера MUST давать явное событие `gap`, а не молча неполную историю. Завершение Рана закрывает стрим терминальным событием статуса.

#### Scenario: Переподключение клиента

- **WHEN** клиент переподключается к стриму с последним увиденным курсором
- **THEN** он получает пропущенные события без дублей и продолжает живой стрим

### Requirement: Секреты не пересекают HTTP-границу

API-ключи LLM (из Ранов и сохранённых подключений) MUST NOT возвращаться в ответах ни в каком виде, кроме маски; в запросах ключ — write-only.

#### Scenario: Чтение Рана с ключом

- **WHEN** клиент запрашивает Ран, у которого в хранилище есть ключ
- **THEN** в ответе присутствует только маска ключа

### Requirement: Граф Рана

Система SHALL отдавать граф Рана: топологию исполняемого графа (узлы и рёбра — из скомпилированного графа) и статусы узлов, выведенные из событий Рана; в агентном режиме делегирования Сабагентам отражаются звездой от Лида.

#### Scenario: Граф пайплайна

- **WHEN** клиент запрашивает граф Рана в режиме пайплайна
- **THEN** ответ содержит узлы scan → parse → report с их текущими статусами

### Requirement: Справочники

Система SHALL отдавать справочники для UI: песочницы, Пресеты памяти, каталог возможностей (типы Сабагентов, тулсет, фичи), сохранённые LLM-подключения (создание/удаление/проверка доступности endpoint).

#### Scenario: Список пресетов

- **WHEN** клиент запрашивает Пресеты памяти
- **THEN** ответ перечисляет именованные пресеты с пометкой продакшен-статуса

### Requirement: Выбор режима Рана через HTTP

Submit через HTTP SHALL принимать режим Рана (pipeline — дефолт, agent) и исполнять Ран соответствующим профилем; Возобновление MUST продолжать Ран его исходным режимом. Граф агентного Рана отдаётся звездой Лид → Сабагенты.

#### Scenario: Агентный Ран из UI

- **WHEN** клиент отправляет POST /runs с mode=agent
- **THEN** Ран ведёт Лид, стрим несёт task_*-события, а граф — звезду делегирований

#### Scenario: Resume агентного Рана

- **WHEN** клиент вызывает resume для упавшего агентного Рана
- **THEN** Ран возобновляется агентным профилем, а не дефолтным pipeline

### Requirement: Удаление Рана

Система SHALL позволять удалить завершённый Ран вместе с его историей и чекпоинтами. Активный (pending/running) Ран удалять NELZYA без предварительной отмены — попытка MUST возвращать ошибку, а не удалять данные исполняющегося Рана.

#### Scenario: Удаление завершённого Рана

- **WHEN** клиент удаляет Ран в терминальном статусе
- **THEN** Ран, его события и чекпоинты удаляются; последующий запрос Рана даёт 404

#### Scenario: Удаление активного Рана

- **WHEN** клиент пытается удалить исполняющийся Ран
- **THEN** система отказывает с ошибкой; Ран и его данные сохраняются

### Requirement: Наблюдаемый ход Лида

Стрим событий агентного Рана SHALL передавать содержательный ход Лида: его рассуждения, вызовы инструментов с аргументами и результаты — а не только внутренние имена узлов графа. Служебные шаги оркестрации MAY опускаться.

#### Scenario: Лид вызывает инструмент

- **WHEN** Лид читает файл в песочнице
- **THEN** подписчик стрима видит событие с именем инструмента и аргументами, а не безымянный узел
