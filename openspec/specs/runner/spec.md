# runner Specification

## Purpose
Раннер — процесс, слушающий очередь Событий и держащий слоты, в которых исполняются долгоживущие Экземпляры Агентов: клейм и дедуп Событий, подъём агента из Сборки, запись результатов в hub, HTTP API для чата/форварда и саморегистрация в backend.

## Requirements

### Requirement: Консьюмер Событий RabbitMQ

Раннер SHALL потреблять События из topic exchange `events` через одну durable-очередь с биндом `#` (competing consumers, auto-ack). Событие — JSON `{eventId, instanceId, threadId, repositoryId, provider, action, commitSha?, ref?, dedupKey}`. Сообщение, не разбирающееся в Событие, SHALL логироваться и отбрасываться без падения консьюмера.

#### Scenario: Событие принято
- **WHEN** в очередь приходит валидное Событие
- **THEN** раннер начинает его обработку (клейм → дедуп → исполнение)

#### Scenario: Мусорное сообщение
- **WHEN** в очередь приходит сообщение без обязательных полей
- **THEN** раннер логирует warning и продолжает потреблять очередь

### Requirement: Клейм Экземпляра и форвард держателю

Перед исполнением раннер SHALL атомарно заклеймить Экземпляр: CAS `down→running` c установкой `runner_id` в `hub.agent_instances`. Если Экземпляр уже `running` на этом же раннере, Событие SHALL обрабатываться локально без повторного клейма. Если Экземпляр `running` на другом раннере, Событие SHALL быть отправлено держателю `POST {address}/instances/{id}/events` (адрес — из `hub.runners`); при недоступности держателя — warning, Событие не теряет запись в журнале дедупа.

#### Scenario: Успешный клейм
- **WHEN** Событие приходит для Экземпляра со статусом `down`
- **THEN** Экземпляр становится `running` с `runner_id` этого раннера и Событие исполняется здесь

#### Scenario: Экземпляр у другого раннера
- **WHEN** Событие приходит для Экземпляра `running` с чужим `runner_id`
- **THEN** раннер форвардит Событие держателю по его адресу из `hub.runners` и сам его не исполняет

### Requirement: Дедупликация Событий

Раннер SHALL гарантировать однократную обработку События на Экземпляр через журнал `hub.instance_events` (PK `instance_id+dedup_key`): вставка записи журнала до исполнения; конфликт вставки означает дубль — Событие SHALL быть пропущено. После успешного исполнения раннер SHALL проставить `processed_at`.

#### Scenario: Дубль События
- **WHEN** приходит Событие с `dedupKey`, уже записанным для этого Экземпляра
- **THEN** раннер пропускает его без исполнения

#### Scenario: Успешная обработка
- **WHEN** Событие исполнено без ошибки
- **THEN** запись журнала получает `processed_at`

### Requirement: Исполнение События Экземпляром

Раннер SHALL поднимать агента из Сборки Экземпляра: LLM — из `hub.llm_connections`, песочница — из `hub.sandbox_connections` (поля `*_enc` расшифровываются AES-GCM-ключом из env), граф — существующий lead-профиль с `thread_id` из События (чекпоинт-тред Экземпляра копит знание между Событиями). Репозиторий SHALL быть доступен в песочнице на коммите События (если задан). Находки агент SHALL писать тулзой `report_finding` в `hub.findings`, отчёт — тулзой `write_report` в `hub.reports`, обе привязаны к `instance_id` (и `event_id`, если есть). Ошибка исполнения SHALL оставлять запись журнала без `processed_at` (для ре-публикации backend'ом) и логироваться.

#### Scenario: Событие исполнено
- **WHEN** Событие заклеймлено и не дубль
- **THEN** агент из Сборки исполняет его в треде Экземпляра, а результаты появляются в `hub.findings`/`hub.reports`

#### Scenario: Ошибка исполнения
- **WHEN** исполнение падает с исключением
- **THEN** `processed_at` не проставляется, ошибка логируется, слот освобождается

### Requirement: Слоты и idle-выгрузка

Раннер SHALL держать не более N (env) одновременно поднятых Экземпляров. Экземпляр без активности (Событий и чата) дольше idle-таймаута (env) SHALL быть выгружен: CAS `running→down` (только при своём `runner_id`), локальные ресурсы отпущены, слот освобождён. Песочница при выгрузке НЕ убивается (no-TTL, жизненным циклом рулит оператор).

#### Scenario: Idle-таймаут
- **WHEN** у поднятого Экземпляра нет активности дольше таймаута
- **THEN** Экземпляр переводится в `down` и слот освобождается

#### Scenario: Слоты заняты
- **WHEN** Событие требует поднять Экземпляр, а все слоты заняты
- **THEN** обработка ждёт свободного слота (не падает и не теряет Событие)

### Requirement: HTTP API раннера

Раннер SHALL предоставлять HTTP API: `POST /instances/{id}/raise` (поднять Экземпляр), `POST /instances/{id}/events` (принять форвардженное Событие), `POST /instances/{id}/chat` (SSE-стрим хода чата в тред Экземпляра), `POST /instances/{id}/stop` (выгрузить), `GET /health` (живость + занятость слотов). Чат SHALL идти в тот же чекпоинт-тред Экземпляра и продлевать его активность.

#### Scenario: Чат с Экземпляром
- **WHEN** приходит `POST /instances/{id}/chat` с сообщением
- **THEN** ход агента стримится SSE и записывается в тред Экземпляра

#### Scenario: Health
- **WHEN** приходит `GET /health`
- **THEN** ответ содержит имя раннера, всего/занято слотов

### Requirement: Регистрация и heartbeat

Раннер SHALL при старте регистрироваться в backend (`POST {backend}/api/runners`: имя, адрес API, слоты; заголовок `X-Runner-Token` из env) и периодически слать heartbeat. Недоступность backend SHALL деградировать в warning с ретраем — раннер продолжает потреблять очередь и обслуживать API.

#### Scenario: Backend недоступен
- **WHEN** регистрация или heartbeat падают сетевой ошибкой
- **THEN** раннер логирует warning, ретраит по интервалу и продолжает работу
